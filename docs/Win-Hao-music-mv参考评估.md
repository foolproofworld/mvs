# Win-Hao/music-mv 参考评估

查看日期：2026-10-23。
来源：[Win-Hao/music-mv](https://github.com/Win-Hao/music-mv)。
本次检查版本：`0088b1422f7f82cdf51b456436a6313127a26d6b`（main 在检查时的提交）。

## 结论

将此仓库作为本项目的**首要创作流程参考**：先理解歌曲，再定画风、统一角色、写分镜、出草图、制作难点样片、逐段完善。它补足了之前参考资料偏重同步工程、缺少叙事和美术方法的问题。

交付仍按本项目要求：浏览器实时绘制的纯前端 MV。采用 Canvas 2D + 独立歌词层作为优先实现方向；HyperFrames / FFmpeg 只在有导出或离线检查需求时引入。此前的 Remotion 路线保留为备选，不再默认需要安装。

本轮是源码阅读与方案修订，没有安装该 skill、执行第三方脚本、运行示例或验证其渲染性能。已读 README、SKILL.md、分镜／角色／渲染／审片说明、歌曲分析脚本、视频节奏脚本、Canvas 模板、歌词层以及许可证。示例的四种画风来自仓库说明，本轮没有逐一渲染核验。

## 值得采用的做法

1. **歌曲决定镜头。** 不只找 BPM，还分析强弱、低音撤出、重新进入、重音和段落。歌词的含义决定画面发生什么，音乐决定动作力度和变化时机。
2. **同一开场试画风。** 用相同构图比较像素、纸艺拼贴、蜡笔绘本等，比较的是实际绘制语言，而非只换滤镜。实时网页优先比较 Canvas 易于实现的像素与纸艺拼贴。
3. **统一角色组件。** 有叙事角色时，使用共享绘制接口，包含朝向、表情、动作进度、道具挂点。各镜头引用同一造型，不重复重画。
4. **统一镜头空间。** 角色、背景、道具共用场景坐标和 camera(t)；歌词处于屏幕空间，不随镜头推拉。允许代码中使用离屏缓存，避免把“一个画布”误解成不能优化绘制。
5. **先草图、后精细动画。** 先看关键帧是否讲得清故事，再做连续动作。样片覆盖最难转场和最强情绪，避免从头堆到尾才发现风格不合适。
6. **审片有证据。** 保留关键帧、转场前后连续抽帧、歌词检查、异常时间点；每次修改能说明位置和原因。

## 必须针对本项目修改的部分

### 1. 原模板不是可直接交付的独立网页播放器

[`templates/hf-canvas/index.html`](https://github.com/Win-Hao/music-mv/blob/0088b1422f7f82cdf51b456436a6313127a26d6b/templates/hf-canvas/index.html) 创建暂停的 GSAP timeline，注册 `window.__timelines.main` 并监听 `hf-seek`。它依靠 HyperFrames 驱动，没有自行实现以 `audio.currentTime` 驱动画面的播放循环。

本项目需要增加：点击播放／暂停、媒体时间驱动 `renderAt(t)`、进度拖动、结束处理、资源就绪状态、响应式缩放；预览和抽帧都使用同一渲染入口。若引入第三方库，优先随项目打包，避免运行依赖外部 CDN。

### 2. “逐字弹出”不等于“逐字歌词同步”

[`templates/lyrics-layer.js`](https://github.com/Win-Hao/music-mv/blob/0088b1422f7f82cdf51b456436a6313127a26d6b/templates/lyrics-layer.js) 按 `t - lineStart - characterIndex * 0.045` 控制逐字弹出，并在下一句前 0.24 秒收走。它使用句级字幕加固定的文字动画速度，没有逐字演唱时间；长音、快唱、停顿都可能不符。

本项目改为真实 `words[].start/end` 驱动显示或高亮，逐句时间仍为权威来源之一；缺少可信词级对齐时先整句显示并标明待校准，不用固定字速假装精确对齐。字幕文本通过 `textContent` / 文本节点写入，避免照搬字符串拼接 `innerHTML`。

### 3. 模板没有消费实际 beat 数组

Canvas 模板以 `BEAT = 60 / BPM` 和 `OFF` 算 `beatPhase(t)`。这能表示固定节拍网格，但分析脚本生成的实测 `beats` 并没有直接进入这段模板。

本项目优先查找实际相邻拍点，计算局部相位；冲击动作使用实际 onset 或 beat 的衰减包络。平均 BPM 只用于描述和缺数据时的预览。统一处理首拍前的负相位，不照搬 JavaScript 负余数逻辑。

### 4. 自动分析输出是候选，不能直接当乐曲事实

[`scripts/analyze_song.py`](https://github.com/Win-Hao/music-mv/blob/0088b1422f7f82cdf51b456436a6313127a26d6b/scripts/analyze_song.py) 使用 librosa，值得参考其 beat、MFCC/chroma 分段、能量突变和重音提取流程；但需注意：

- 小节第一拍按 **4/4** 预设，通过低频起音在四种相位中取最大值，不是通用拍号／downbeat 识别。
- 分段数量默认根据歌曲时长设定，最多 12 段；聚类边界不等于已确认的主歌、副歌。
- `--tempo-hint` 传给 `beat_track` 的是 `start_bpm`，属于估计初始值，不保证锁定到指定 BPM。
- 脚本没有做歌词识别、词级强制对齐或歌词情绪理解，这些是独立工作。

因此保留分析版本、来源与核验状态；对首拍、半速／倍速、弱起、拍号、段落标签进行校准。

### 5. 节奏检查无法单独证明歌词和拍点准确

[`scripts/video_rhythm.py`](https://github.com/Win-Hao/music-mv/blob/0088b1422f7f82cdf51b456436a6313127a26d6b/scripts/video_rhythm.py) 通过低分辨率灰度帧差估计切点、静止区间和黑帧，并检查切点距离 beat 是否足够近。它不能检测语义是否贴合歌词，也不能测出每个字是否对上歌声。

暗色风格、故意留白、慢镜头、闪光都可能触发误报。把它作为问题定位工具，结合设计意图、浏览器实播和歌词时间轴核验；不为了通过阈值而强行加粒子或摇镜头。

### 6. 离线逐帧绘制能力不等于实时性能

原仓库给 p5.brush 等异步／较慢画法提供先渲逐帧再合成的路线。这与浏览器实时画完整 MV 的性能要求不同。本项目先验证样片的实时开销，必要时缓存纸纹、笔触和背景，降低绘制分辨率；不默认把整段画面预渲成视频替代前端绘制。

## 修订后的制作节奏

| 阶段 | 本项目产物 | 本仓库带来的增强 |
| --- | --- | --- |
| 1 解析整首歌 | 源信息、准确歌词、逐拍／逐词候选、真实段落与情绪变化 | 加入突然安静、低音撤掉、重新进入、重音等分镜线索 |
| 2 定视觉语言 | 相同开场的风格关键帧、颜色／纹理／文字规则 | 先比较实际画法，再确定风格 |
| 3 定角色与场景 | 共用角色组件或视觉母题、表情动作表、统一镜头坐标 | 避免各镜头造型漂移、道具与角色脱离 |
| 4 写全曲分镜 | 每句／乐句的语义、主要动作、起止、景别、音乐触发、转场 | 每句有明确的视觉表达；无需机械地一句一硬切，可以连续运镜 |
| 5 草图与难点样片 | 全曲关键帧接触表、20–40 秒代表样片（含约 10–20 秒最难片段） | 先核实叙事和绘制能力，再投入整曲 |
| 6 全曲制作与审看 | 完整前端页面、同步校准、性能记录与时间点问题单 | 每版能定位问题；原曲直接播放，导出 MP4 时才考虑重新封装音轨 |

歌词、画风等需要用户选择时，应提供已有的具体样图或时间轴。此次参考评估不安装整套上游 skill，也不把上游每个停点机械转成当前工作的阻塞条件。
